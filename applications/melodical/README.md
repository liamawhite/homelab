# Melodical

Short music theory practice for piano and guitar. Build intuition for keys, intervals, triads, inversions, and notes on the guitar neck, at an instrument or away from it.

Go serves a bundled React application. The runtime is one CGO-free binary with embedded frontend assets and a pure-Go SQLite driver. SQLite queries are generated by sqlc, behind the `store.Store` interface so another storage adapter can be added later.

Run the commands below from `applications/melodical`. This application has its own
Go module and lockfiles; local commands and CI use `GOWORK=off`.

## Run locally

Requires Go 1.26.8+ and Node 22.12+ (or another Node version supported by Vite).

```sh
make dev
```

Open the URL printed by Vite (http://localhost:5173 by default, or the next available port). Set `MELODICAL_DEV_PORT` to require a particular frontend port. `make dev` installs frontend dependencies, prepares embedded assets, and starts both servers. React updates through Vite hot reload; Go rebuilds and restarts when backend source or SQL files change. Failed Go builds leave the previous server running. Ctrl-C stops both servers.

The API listens on 127.0.0.1:8080 by default. Progress is stored in `data/melodical.db` by default. Change the address or database path with `MELODICAL_ADDR` and `MELODICAL_DB`.

Vite proxies `/api` to the Go server, including when `MELODICAL_ADDR` selects a different backend port. Use `make run` to build and run the production binary at http://localhost:8080.

## Container build

```sh
docker build -t melodical .
```

The image runs one static Go binary as UID/GID 65532, serves port 8080, and stores SQLite data at `/data/melodical.db`. The runtime image is `scratch`; no C library, Node, or external asset files are needed. Mount writable persistent storage at `/data`.

Changes to `applications/melodical/` on `main` build and publishes Linux amd64/arm64 images to `ghcr.io/liamawhite/melodical` through [the publishing workflow](../../.github/workflows/melodical-publish.yml). The image build runs backend tests and the frontend typecheck/build before publishing. Each run publishes `sha-<full commit SHA>`; the current head of `main` also updates `latest`. Manual runs on `main` are supported. Publishing uses the homelab `GHCR_TOKEN` Actions secret, falling back to `GITHUB_TOKEN` when the package grants homelab write access. OCI labels link the package to this repository.

Use a commit tag or image digest in the deployment repository when you want a fixed version. GitHub creates new container packages as private by default; configure package visibility or registry credentials in the deployment repository as appropriate.

Homelab deployment is managed in a separate repository using k3s. This repository contains no cluster manifests or deployment orchestration. Authentication remains out of scope for the private Tailscale setup.

## Practice

- Quick rounds, timed sessions, and open-ended practice, with remembered settings.
- Piano, guitar, or both; focused topics or adaptive mixed review.
- Manual key/difficulty selection or automatic recommendations.
- Keyboard and right-handed fretboard answers. Hints, explanations, and optional synthesized sound.
- Chord construction accepts valid spacings and doublings; inversion questions require the correct bass. Guitar chords allow one position per string.
- Progress shared across devices; unfinished sessions resume on the same device.
- Recognition timing excludes assisted and interrupted attempts. Timed sessions never impose per-answer deadlines.
- Field notes connect the exercises to real-instrument practice.

Automatic difficulty starts with familiar keys, then broadens as you practice. Level 3 introduces scale-degree prompts and Roman-numeral chord roles. Review mixes due and weak areas with new material. It is a simple initial heuristic, with proficiency recorded separately by instrument/topic/key. MIDI/audio detection, offline practice, minor-key exercises, and advanced harmony are deferred.

## Development and verification

```sh
make format          # apply gofmt and Prettier
make format-check    # verify formatting without changing files
make lint            # golangci-lint + ESLint; frontend build/typecheck
make generate        # sqlc 1.31.1; generated files are included in source
make test            # CGO_ENABLED=0 backend tests, vet, frontend typecheck/build
make test-browser    # Chromium desktop, tablet, and phone browser flows
make static-linux    # standalone Linux amd64 executable
```

Pull requests run separate **Format**, **Lint**, and **Tests** checks through [the PR workflow](.github/workflows/pr-checks.yml). Tests include backend coverage and all nine Playwright flows across desktop, tablet, and phone viewports. Browser screenshots and traces are uploaded on failure. Focused Playwright tests (`test.only`) are rejected in CI. Local Go linting requires golangci-lint 2.14.0; frontend tooling is installed with `npm ci --prefix web`.

Install the test browser once with `cd web && npx playwright install chromium`. Browser tests use an isolated SQLite database in `.tmp/`. The test suite checks generated exercise solutions, inversion/voicing validation, guitar coordinates, durable/idempotent saves, assisted/interrupted timing, and the HTTP API.

The SQLite schema in `internal/store/sql/schema.sql` is embedded and initialized on first run. This first version has one schema; future schema changes require versioned migrations before changing existing tables. `internal/store/sql/queries.sql` is the source of truth for generated database access; edit it and run sqlc rather than editing generated Go.
